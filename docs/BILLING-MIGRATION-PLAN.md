### 1.4 רשימת היכולות המלאה (מה חייב להישמר)
**כללי**
1. לוח מחוונים: הכנסות כוללות, ממוצע זמן טיפול, קריאות פתוחות, חשבוניות שטרם שולמו, התפלגות מוצרים ללקוחות, גרף הכנסות.
2. לקוחות: חיפוש, הוספה/עריכה/מחיקה, שיוך מוצרים ללקוח עם מספר משתמשים ומשתמשי Light ותאריך התחלה.
3. מוצרים: הוספה/עריכה/מחיקה, מחיר למשתמש, משתמש Light ומחירו, כמה לקוחות משתמשים בכל מוצר.
4. שירותים: הוספה/עריכה/מחיקה, מחיר, "חיוב מתחדש".
5. הוצאות: הוספה/עריכה/מחיקה, מטבע (₪/$/€) והמרה לש"ח, קטגוריות (תוכנה, דאטהבייס, עובדים, ציוד, משרד, אחר), הוצאה חוזרת, סינון וממיון, ייצוא לאקסל, סיכומים.

**ניהול**
6. חיובים: רשימת סיכומים חודשיים ללקוח, סינון שולם/טרם שולם, סימון שולם (עם תאריך תשלום), פרטי חיוב (שורות לפי מוצר + שירותים נוספים), עריכת חודש/שנה/סטטוס, מחיקה (כולל שורות החיוב של אותו חודש). כפתורי "חיוב חדש" ו"הפק PDF" קיימים במסך אבל **לא ממומשים**.
7. דוחות חיוב (שעות): בחירת לקוח וטווח תאריכים, רשימת רישומי זמן עם קריאה/עובד/תיאור, סיכום שעות, הדפסה, ייצוא PDF, ייצוא אקסל.
8. קריאות שירות: רשימה עם סינון סטטוס וחיפוש, סטטיסטיקות (פעילות/נפתרו/נסגרו/סה"כ זמן), פתיחת קריאה (לקוח, מוצר, תאריך, כותרת, איש קשר, טלפון, קבוצה, תיאור, תמונה, עדיפות, מטפל, זמן ראשוני), עריכה/מחיקה, הוספת/עריכת/מחיקת רישומי זמן, רישום זמן מהיר, קישור עדכון חיצוני (העתקה או שליחה בוואטסאפ), הדפסת דוח קריאות.
9. רשימת פעילויות: פיד מאוחד של קריאות, רישומי זמן ועדכונים חיצוניים, עם חיפוש וסינון לפי קריאה וסוג.
10. דף עדכון חיצוני (ציבורי, ללא התחברות): הלקוח מדווח תאריך טיפול, שם מטפל, זמן טיפול ותוכן.
11. מאגר ידע: מאמרים לפי מוצר, קטגוריה ותגיות, חיפוש וסינון (היום בזיכרון בלבד).
12. דוחות: הכנסות (עמודות), קריאות שירות (קו), לקוחות, עם בחירת טווח זמן.

**הגדרות**
13. עובדים: הוספה/עריכה/מחיקה, תפקיד, קישור לעובד משתמש מערכת (יצירת משתמש התחברות), "קשר את כל העובדים".
14. הזדהות: כניסה/הרשמה באימייל וסיסמה, ניתוק.

### 1.5 בעיות קיימות שהמעבר צריך לתקן (לא לשחזר)
- מסך החיובים מציג שמות לקוחות ומוצרים **מנתוני דמו** ולא מה-DB (לכן מופיע "לא ידוע").
- אין מנוע שמייצר חיוב חודשי: הסיכומים ושורות החיוב נוצרים ידנית, ו"חיוב חדש" לא עובד.
- לוח המחוונים והדוחות מערבבים נתוני אמת עם נתוני דמו (גרפים קבועים).
- שערי מטבע קשיחים בקוד (3.7 ל-$, 4.0 ל-€).
- מאגר הידע לא נשמר.
- אבטחה: מדיניות RLS מתירה לכל אחד (גם לא מחובר) לקרוא ולשנות קריאות שירות, רישומי זמן ותמונות; יצירת משתמשים נעשית מהדפדפן עם `auth.admin` (דורש מפתח service role בצד לקוח); הסיסמה של המנהל כתובה במיגרציה בריפו.
- הקישור החיצוני הוא מזהה הקריאה הגולמי: מי שמנחש מזהה יכול לכתוב עדכונים.

## 2. ארכיטקטורת היעד

**עיקרון:** מודול `billing` בתוך מרכז הבקרה, באותה תבנית של מודול ה-PT ושל ה-CC: טבלאות עם קידומת, נתיבי API תחת `/billing`, דפי React תחת `/billing/*`, אותו משתמש ואותן הרשאות, אותו עיצוב.

### 2.1 בסיס הנתונים (Supabase `pt`, סכמת public, בעלות `pt_app`)
כל טבלה מקבלת `organization_id` ו-`workspace_id` (כמו שאר המערכת), `id` טקסטואלי עם קידומת, עמודות טיפוסיות + `data jsonb`. ה-UUID המקורי נשמר ב-`legacy_id` כדי שאפשר יהיה לאמת את ההעברה.

| טבלה חדשה | מקור | הערות |
|---|---|---|
| `bl_customers` | customers | אפשרות לקשר ל-`clients` הקיימת (מדידת שימוש לפי לקוח) דרך `client_id`. ברירת מחדל: יצירת client לכל לקוח חיוב, כך שדוח השימוש (Claude/WhatsApp) ודוח החיוב מדברים על אותו לקוח |
| `bl_products` | products | |
| `bl_subscriptions` | product_users | שם מדויק יותר: מנוי של לקוח למוצר עם כמות משתמשים, Light, תוקף |
| `bl_services` | services | |
| `bl_employees` | employees | `user_id` → `users` של מרכז הבקרה במקום profiles |
| `bl_tickets` | service_tickets | + `number` רץ (SC-000123) + `external_token` |
| `bl_time_entries` | service_time_entries | |
| `bl_external_updates` | external_ticket_updates | |
| `bl_charges` | monthly_summaries | + `status` (draft/issued/paid/cancelled), `issued_at`, `notes`, `source` (auto/manual) |
| `bl_charge_lines` | billing_items | + `charge_id` ישיר (היום הקשר הוא רק לפי תאריך), `kind` (product/service/hours/manual), `description`, `quantity`, `unit_price`, `total` |
| `bl_expenses` | expenses | + `rate_used` (השער ששימש להמרה) |
| `bl_knowledge` | knowledge_items | + `category` |
| `bl_fx_rates` | חדש | שערי מטבע יומיים (בנק ישראל), נשלפים ב-cron |
| `bl_settings` | חדש | הגדרות: מע"מ, מטבע ברירת מחדל, תעריף שעה ברירת מחדל, תבנית מספר קריאה |

קבצים: תמונות קריאה נשמרות ב-Supabase Storage של פרויקט `pt`, דלי **פרטי** `billing-ticket-images`, העלאה והורדה דרך השרת עם URL חתום לזמן קצוב.

### 2.2 הרשאות
- אותם משתמשים של מרכז הבקרה. אין Supabase Auth נפרד.
- המודול חי בתוך **מרחב** (למשל "Comax" או "פרטי"). מי שעורך במרחב רואה ועורך חיובים. צפייה בלבד לתפקידי צפייה.
- עובד = שורה ב-`bl_employees`, אופציונלית מקושר למשתמש מערכת. "קשר עובד למשתמש" יוצר הזמנה דרך מסך המשתמשים הקיים, לא יצירת משתמש מהדפדפן.
- דף העדכון החיצוני: קישור `/u/<token>` כש-token הוא HMAC של מזהה הקריאה עם `PT_ORG_HMAC_KEY`, עם תוקף. בלי טוקן תקף אין כתיבה.

### 2.3 שילובים עם מה שכבר קיים במרכז הבקרה
- **לקוחות ↔ clients:** דף הלקוח מציג גם את צריכת ה-API/וואטסאפ מדוח השימוש. אפשר להוסיף שורת חיוב אוטומטית "שימוש" מתוך `usage_entries` (לפי תעריף ליחידה שמוגדר במוצר).
- **הוצאות ↔ cost_entries:** עלויות הענן שהמערכת כבר אוספת (Vercel, Anthropic) יופיעו בדוח ההוצאות כקטגוריה "תשתית" בלי הקלדה ידנית.
- **קריאות שירות ↔ התראות:** קריאה קריטית פתוחה מעל X שעות מייצרת התראה בתיבת ההתראות הקיימת (webhook/אימייל).
- **פרויקטים ↔ מוצרים:** מוצר יכול להצביע על פרויקט במרכז הבקרה, כך שמדף המוצר רואים איפה הקוד, הפריסה והסריקות.

## 3. מנוע החיוב (החלק שחסר היום)

1. **יצירת חיוב חודשי** (`POST /billing/charges/generate?month=2026-11`): לכל לקוח עם מנויים פעילים בחודש:
   - שורה לכל מוצר: `user_count × price` + `light_user_count × light_user_price` (יחסית לתוקף בתוך החודש).
   - שורה לכל שירות מתחדש של הלקוח.
   - שורת "שעות" אופציונלית: סך רישומי הזמן בחודש × תעריף שעה (של העובד או ברירת המחדל), אם הלקוח מסומן "חיוב לפי שעות".
   - שורות ידניות שנוספו מראש לחודש.
   - סכום, מע"מ לפי הגדרה, סטטוס `draft`. הרצה חוזרת על אותו חודש מעדכנת טיוטה ולא יוצרת כפילות; חיוב שכבר `issued`/`paid` לא נוגעים בו.
2. **סימון הופק / שולם / בוטל** עם תאריך, וסימון חלקי של שורות.
3. **PDF לחיוב** (RTL, לוגו, פירוט שורות) ו-**Excel** לכל רשימה, בצד שרת.
4. **דוח שעות ללקוח** לטווח תאריכים (קיים היום) + גרסה מסכמת לפי עובד ולפי קריאה.
5. **המרת מטבע** לפי שער היום של ההוצאה (`bl_fx_rates`), עם אפשרות לדרוס ידנית.
6. (אופציונלי, מתוך billing-ledger-manager) **הצמדה למדד**: מחיר בסיס + מדד בסיס, חישוב מחיר ממודד לפי מדד נוכחי; **דוח עמלות סוכנים**.

### סדר הנתונים בייבוא
employees → customers → products → services → subscriptions → tickets → time_entries → external_updates → charges → charge_lines (מקושרות לחיוב לפי לקוח+חודש) → expenses → knowledge. אחרי כל טבלה: השוואת מספר שורות, ולטבלאות כספיות גם סכום כולל.

## 5. איך זה ייראה במרכז הבקרה

- בתפריט הצד קבוצה חדשה **"חיוב ושירות"**: לוח חיוב, לקוחות, מוצרים ושירותים, קריאות שירות, פעילויות, חיובים, דוחות, הוצאות, מאגר ידע, עובדים.
- אותו עיצוב כמו הלוח החדש: כרטיסים, אריחי מדדים עם מגמה (הכנסות החודש, חיובים פתוחים, קריאות פתוחות, שעות החודש), לוגו וואטסאפ בקישור העדכון.
- בדף לקוח: טאבים "מנויים", "קריאות", "חיובים", "שימוש" (מתוך המדידה הקיימת).
- בדף פרויקט במרכז הבקרה: אם המוצר מקושר לפרויקט, קישור הדדי.

## 6. מה צריך ממך לפני שמתחילים

1. **גישה לנתונים הישנים.** פרויקט Supabase `qmkutgtibzknmuqzzasp` לא נגיש דרך החיבור שלי. אחת משתי אפשרויות:
   - להוסיף אותי (ה-MCP של Supabase) לארגון שבו הפרויקט יושב, או
   - לייצא מ-Supabase Dashboard → Table Editor → Export CSV לכל אחת מ-12 הטבלאות, ולהוריד את תיקיית `ticket-images` מה-Storage. לשים הכול בתיקייה אחת ולתת לי.
   כל עוד אין יצוא, אפשר לבצע את שלבים 1 עד 5 על נתוני בדיקה, והייבוא ייעשה בסוף.
2. **החלטות עסקיות קצרות** (אפשר לענות בשורה אחת כל אחת):
   - האם לקוח חיוב = לקוח במדידת השימוש (אותה רשימה)? ברירת מחדל: כן.
   - האם החיוב החודשי כולל מע"מ ומה האחוז? ברירת מחדל: 18%, מוצג בנפרד.
   - האם לחייב שעות טיפול אוטומטית, ולפי איזה תעריף? ברירת מחדל: לא אוטומטי, שורה ידנית.
   - אילו עובדים צריכים כניסה למערכת (מעבר לך)?
   - האם רוצים את ההצמדה למדד ודוח העמלות מ-billing-ledger-manager? ברירת מחדל: לא בשלב הראשון.
   - איזה מרחב מקבל את המודול: "פרטי" או מרחב חדש "חיוב"?
3. **אחרי המעבר**: אישור לארכב את `billing-knowledge-hub` ו-`billing-ledger-manager` ב-GitHub (מתוך מרכז הבקרה, אזור מסוכן) ולהשהות את הפרויקט הישן ב-Supabase.

## 7. קריטריוני קבלה
- כל 14 היכולות בסעיף 1.4 עובדות במרכז הבקרה על הנתונים האמיתיים.
- ספירת שורות וסכומי `total_amount`, `amount_in_ils`, `time_spent` זהים בין הישן לחדש בתאריך המעבר.
- אין נתוני דמו באף מסך.
- כל קריאת API דורשת התחברות למעט דף העדכון החיצוני, שדורש טוקן חתום.
- בדיקות: יחידה למנוע החיוב (חודש חלקי, Light, שירות מתחדש, הרצה חוזרת), API לכל ישות, E2E בדפדפן: לקוח → מנוי → קריאה → רישום זמן → הפקת חיוב → PDF.
- העיצוב עובר בדיקת טלפון (390px) ושולחן עבודה.
